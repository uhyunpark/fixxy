# 상용 플러그인 UI는 실제로 어떻게 만들어지는가 — 세 가지 방식

주기적으로 다시 읽는 학습 문서. 용어는 처음 나올 때마다 한 줄로 풀어 쓴다.
목표: "이 UI 고급스럽다"는 감각을 구현 방식으로 분해해서, 우리 선택(코드 드로잉)의 이유를
설계 근거로 남기기.

---

## TL;DR — 세 방식 요약

| 방식 | 대표 | 핵심 | 대가 |
|---|---|---|---|
| 1. 이미지 기반 | El Rey, UAD, Acustica, 구형 Waves | 하드웨어를 렌더/촬영 → 각도별 프레임을 필름스트립으로 이어붙임 | 리사이즈 불가, 수십~수백 MB, 레이아웃 변경 = 재렌더 |
| 2. 코드 드로잉 | FabFilter, ZL, 우리 LpngLookAndFeel | 모든 픽셀을 벡터 코드로 매 프레임 계산 | "굉장해 보임"은 디테일 밀도에서 나옴 — 공짜가 아니다 |
| 3. GPU 렌더링 | Pro-Q 스펙트럼, Soothe 델타 | 초당 수만 포인트를 OpenGL/Metal로 | 구현 복잡도, 필요할 때만 |

우리는 2번이다. 메타 플러그인은 UI를 코드가 런타임에 조립해야 하는데, 이미지 방식은 조립할
"그림"이 존재하지 않는다 — 자세한 이유는 아래 "우리 스택에서의 대응물" 참고.

---

## 1. 이미지 기반 (스큐어모픽/빈티지 계열)

**용어 먼저.**

- **필름스트립(filmstrip)**: 노브 하나가 돌아가는 전 구간(예: 0~270도)을 수십~수백 장의
  정지 이미지로 찍어 세로/가로로 이어붙인 하나의 큰 이미지 파일. 물리적 비유: 옛날 영화
  필름 — 한 컷 한 컷이 각도별 스냅샷이고, 재생이 아니라 값에 따라 딱 한 프레임만 잘라서
  보여주는 것.

El Rey, UAD, Acustica, 구형 Waves 같은 빈티지/스큐어모픽 계열의 방법: 실제 하드웨어를
3D로 렌더(주로 Blender)하거나 실물을 촬영한다. 노브 하나마다 회전 각도별로 수십 장의
프레임을 만들고, 사용자가 노브를 돌리면 현재 값에 맞는 프레임 한 장을 잘라 화면에 붙인다.
VU 미터 바늘도 같은 방식 — 바늘 각도별 프레임을 스트립으로 갖고 있다가 값에 맞춰 잘라 쓴다.

**대가**:

- **리사이즈 불가**: 벡터가 아니라 픽셀이라, 창을 늘리면 이미지가 흐려진다. 해상도별로
  에셋을 따로 만들어 둬야 한다(예: 1x/2x/레티나).
- **바이너리가 크다**: 노브 하나에 프레임 수십 장, 플러그인 전체로는 수백 개의 이미지 —
  수십~수백 MB가 흔하다.
- **레이아웃을 바꾸려면 재렌더**: 노브 위치를 옮기거나 새 컨트롤을 추가하면 그림을 다시
  찍어야 한다. 코드 몇 줄로 끝날 일이 아니다.

---

## 2. 코드 드로잉 (모던 계열) — 우리가 쓰는 방식

**용어 먼저.**

- **벡터 드로잉(vector drawing)**: 이미지를 미리 저장해두지 않고, "이 위치에서 이 반지름의
  호를 그려라" 같은 수학적 명령을 매 프레임 실행해서 픽셀을 만드는 것. 물리적 비유: 사진을
  붙이는 대신, 화가가 매번 다시 그리는 것 — 대신 그 화가는 초당 수십 번 그릴 수 있다.

FabFilter, ZL, 우리 `LpngLookAndFeel` 계열의 방법: 노브, 그래프, 미터 등 모든 픽셀을
`juce::Graphics`의 호출(선 긋기, 호 그리기, 채우기 등)로 직접 그린다. 이미지 파일이 없다.

**대가는 장점 쪽**: 창을 아무리 늘려도 흐려지지 않고(무한 리사이즈), 이미지 에셋이 없어
바이너리가 작다.

**"굉장해 보이는" 비결은 이미지가 아니라 디테일 밀도다.** 코드 드로잉 자체는 특별할 게
없다 — 사각형 하나 그리는 코드는 아마추어 플러그인도 쓴다. FabFilter급으로 보이는 차이는:

- 서브픽셀 안티앨리어싱(선 가장자리를 부드럽게 만드는 렌더링 처리)
- 신중하게 고른 그라데이션의 유무·강도
- 일관된 spacing(여백 규칙을 끝까지 지키는 것)
- 절제된 애니메이션 — 미터가 값에 반응하는 감쇠 곡선 하나까지 디자인된 것

즉 "코드로 그린다"는 방법의 선택이고, "잘 그린다"는 별도의 노력이다. 이 문서 뒷부분의
체크리스트가 그 노력의 목록이다.

---

## 3. GPU 렌더링 (무거운 시각화)

**용어 먼저.**

- **GPU 컨텍스트(GPU context)**: 화면을 그리는 작업을 CPU가 아니라 그래픽카드에 맡기는
  실행 환경. JUCE에서는 `juce::OpenGLContext`를 컴포넌트에 붙이면 그 컴포넌트의 페인트가
  OpenGL로 처리된다.

Pro-Q의 실시간 스펙트럼, Soothe의 델타 디스플레이처럼 초당 수만 개의 점을 그려야 하는
시각화는 CPU 페인트(`Component::paint`)로 감당하기 버겁다 — 매 프레임 수만 개의 점/선을
CPU에서 계산해 래스터화하면 프레임이 밀린다. 이럴 때 OpenGL/Metal 같은 GPU API로 넘긴다.

**우리 프로젝트에서는**: 지금 애널라이저는 512포인트를 30Hz로 CPU 페인트하는 것으로
충분하다 — 이 정도 포인트 수/갱신률은 CPU가 여유 있게 처리한다. GPU 컨텍스트가 필요해지는
시점은 스펙트럴 프로세서 단계(더 조밀한 FFT 해상도나 더 높은 갱신률이 필요해질 때)로
미뤄두고 있다.

## 우리 스택에서의 대응물

`src/plugins/LpngLookAndFeel.h`가 2번 방식의 우리 구현이다. 파일 상단 DESIGN SPEC
블록(9~77행)이 계약이다. 핵심 의미 규칙(17~27행):

- **쿨(cool) 블루/그레이 = 신호(signal/data)** — 애널라이저, 응답 곡선, 스펙트럼, 레벨
  미터. `palette::dataPre/dataPost/dataSum/controlFill`.
- **웜(warm) 앰버 = 동작(dynamics/action)** — 게인 리덕션, 스레숄드, 컴프레션 양처럼
  "프로세서가 신호에 지금 하고 있는 일". `palette::accent`. 희소하게 쓴다 — 화면 전체가
  앰버면 신호를 잃은 것이다(spec 26~27행).
- **크롬(chrome, 배경/그리드/틱/보더/라벨)은 모노크롬** — 절대 색을 넣지 않는다. 유일한
  예외가 밴드별 identity 색(`palette::bandColour()`, HSV(i/N, 0.65, 0.95)) — 이것도
  "다른 곳에서 새로 만들지 말고 재사용하라"는 규칙이 붙어 있다(spec 29~33행, 118~125행).

**왜 우리는 2번이어야 하는가**: 메타 플러그인은 자연어 요청에 따라 DSP 그래프를 런타임에
조립한다(`CLAUDE.md`의 프로젝트 정의). UI도 같은 운명이다 — 노드가 추가/제거/재배선되면
그 노드의 컨트롤이 화면에 나타나거나 사라져야 한다. 이미지 기반 방식은 "새 레이아웃 = 재렌더"
가 전제라, 애초에 존재하지 않는 조합의 화면을 코드가 그때그때 만들어내야 하는 상황과
근본적으로 맞지 않는다. 코드 드로잉은 컴포넌트를 새로 배치하는 것이 곧 코드 실행이므로,
동적 조립과 방법론이 자연스럽게 맞아떨어진다. `LpngLookAndFeel`을 하나 붙여두면 새로 추가되는
어떤 노드의 UI도 가져다 쓰기만 하면 자동으로 "한 제품처럼" 보인다(spec 15행: "LpngEQ와
LpngComp는 하나의 제품처럼 읽혀야 한다").

## "FabFilter처럼 보이게 만드는" 디테일 체크리스트

방법(코드 드로잉)을 골랐다고 결과가 따라오지 않는다. FabFilter/ZL급 마감을 가르는 항목들:

1. **서브픽셀 스트로크**: 선이 정수 픽셀 경계에 딱 맞지 않아도 안티앨리어싱으로 부드럽게
   — 계단 현상(jaggies) 없이. JUCE의 `Graphics`는 기본적으로 안티앨리어싱을 켜고 그리므로
   좌표를 정수로 반올림하지 않는 것이 핵심.
2. **그림자/글로우의 절제**: 스펙(72행)이 명시적으로 금지 — "gradients, shadows,
   textures, image assets" 없음. 그림자를 안 쓰는 게 아니라 못 쓰는 게 아니라, 안 쓰는 것이
   "모던" 룩의 정체성이다.
3. **값 변화 애니메이션 커브**: 노브를 돌리거나 미터가 움직일 때 값이 즉시 점프하지 않고
   감쇠 곡선을 그리며 도달한다. 얼마나 빠르게/어떤 곡선으로 도달하는지가 "고급스러움"의
   상당 부분을 만든다 — sound-quality-primer.md의 지퍼 노이즈와 같은 원리: 계단식 변화는
   싸구려 티가 난다.
4. **hover 상태**: 마우스가 올라간 컨트롤은 시각적으로 반응해야 한다(`LpngLookAndFeel`의
   `drawToggleButton`에서 `shouldDrawButtonAsHighlighted`가 보더 색을 바꾸는 것이 예).
   반응이 없으면 "그림"처럼 느껴진다.
5. **타이포 위계**: 라벨용/수치용/헤더용 폰트를 구분해서 쓴다. 우리는 `labelFont()` /
   `valueFont()`(모노스페이스) / `headerFont()` 세 단계(spec 61~64행). 수치 readout에
   모노스페이스를 쓰는 것은 "계기(instrument)"처럼 보이게 만드는 의도적 시그니처 — dB/Hz
   숫자열이 소수점에서 정렬된다.
6. **색 의미론 일관성**: 색이 장식이 아니라 의미를 나르면(위 "우리 스택에서의 대응물" 참고),
   사용자가 화면을 배우지 않고도 "이건 신호, 저건 지금 처리 중인 것"을 직관적으로 구분한다.
   같은 색을 두 가지 뜻으로 쓰는 순간 이 신뢰가 깨진다.
7. **일관된 spacing**: 여백을 감으로 잡지 않고 하나의 기본 단위(우리는 `kSpacing` = 6px)의
   배수로만 쓴다. 눈은 정렬 오차를 논리적으로 설명 못 해도 즉시 감지한다.

## JUCE 구현 매핑 — 언제 뭘 쓰나

세 가지 레벨이 있고, 규모가 커질수록 한 단계 위로 올라간다.

- **`LookAndFeel` 오버라이드** (`LpngLookAndFeel::drawRotarySlider` 등): JUCE 표준
  컴포넌트(`Slider`, `ToggleButton`, `ComboBox`...)의 기본 렌더링을 통째로 바꿀 때. 장점은
  한 번 정의하면 그 룩앤필이 붙은 모든 컴포넌트에 자동 적용된다 — 노브를 몇 개를 새로
  추가해도 스타일을 다시 정의할 필요가 없다. "가족 전체의 시각적 정체성"을 정의하는 계층.
- **`Component::paint` 커스텀 드로잉**: 표준 컴포넌트로 표현이 안 되는 것 — 스펙트럼
  곡선, EQ 응답 그래프, 게인 리덕션 미터처럼 그 플러그인에만 있는 그래픽. 룩앤필 오버라이드로
  덮을 표준 위젯이 애초에 없으니 컴포넌트가 직접 `Graphics`에 그린다. 우리 `AnalyzerView`류가
  여기 해당.
- **`OpenGLContext`**: `paint`가 CPU 페인트로 프레임을 못 따라갈 때만 — 위 "GPU 렌더링"
  절의 포인트 수/갱신률 기준을 넘어설 때. 컴포넌트에 컨텍스트를 붙이면 그 서브트리의 렌더링이
  GPU로 넘어간다. 지금 우리 애널라이저는 이 기준에 못 미치므로 아직 안 쓴다.

경험칙: 표준 위젯이면 LookAndFeel, 커스텀 그래픽인데 CPU로 충분하면 paint, CPU가 밀리기
시작하면 그때 OpenGLContext로 옮긴다. 처음부터 GPU로 가지 않는다 — 필요해지기 전에 쓰는
복잡도는 낭비다.

## 짧은 용어집

- **필름스트립(filmstrip)**: 노브/바늘의 회전 각도별 프레임을 이어붙인 이미지. 값에 따라
  한 프레임을 잘라 표시한다. 이미지 기반 UI의 핵심 자산.
- **LookAndFeel**: JUCE에서 표준 컴포넌트의 렌더링 방식을 통째로 갈아끼우는 클래스.
  하나를 에디터에 붙이면 그 아래 모든 자식 컴포넌트가 같은 스타일로 그려진다.
- **벡터 드로잉(vector drawing)**: 이미지 파일 대신 좌표/도형 명령으로 매 프레임 픽셀을
  계산해 그리는 것. 무한 리사이즈가 가능하고 바이너리가 작다.
- **리페인트 무효화(repaint invalidation)**: 컴포넌트가 "내 화면이 지금 상태와 안 맞으니
  다시 그려달라"고 프레임워크에 요청하는 것(`repaint()`). 값이 바뀔 때마다 매번 전체를
  다시 그리는 게 아니라, 바뀐 부분만 무효화 요청을 걸어 다시 그리게 하는 것이 성능의 핵심.
- **GPU 컨텍스트(GPU context)**: 렌더링을 CPU가 아니라 그래픽카드가 처리하도록 넘기는
  실행 환경. JUCE에서는 `juce::OpenGLContext`.
